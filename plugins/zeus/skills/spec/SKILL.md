## 引数仕様

| 呼び出し | 動作 |
|---|---|
| `/zeus:spec <要望>` | 引数を初期要望として受領、ヒアリング開始 |
| `/zeus:spec` | 引数なしの場合は `AskUserQuestion` でまず「何がしたいか」を聞く |

## 使用エージェント

| エージェント | subagent_type | 役割 |
|---|---|---|
| Zeus Explorer | `zeus-explorer` | 既存コードベースを調査し、関連実装・抽象化・規約を把握 (フィジビリ調査) |
| Zeus Tech Surveyor | `zeus-tech-surveyor` | フィジビリティ調査 (関連ライブラリ・公式推奨パターン・知られた落とし穴) を WebSearch / WebFetch で調査 |
| Zeus Survey Validator | `zeus-survey-validator` | tech-surveyor の主張を出典 URL で検証 |
| Zeus Spec Writer | `zeus-spec-writer` | ヒアリング + 調査結果を構造化された仕様書に整理 |

ヒアリング自体はメインエージェントが `AskUserQuestion` を使って進める。

## ディレクトリ規約

```
.claude/zeus/specs/{YYYYMMDD-HHMMSS}-{slug}/
├── spec.md                ← zeus-spec-writer が作成 (dev には spec.md パスを直接渡す)
├── interview-log.md       ← ヒアリングのやりとり記録
├── raw/                   ← 調査エージェントの生レポート (dev が再利用)
│   ├── explorer.md        ← 既存実装調査（実施時のみ、dev が再利用）
│   ├── survey.md          ← フィジビリティ調査一次レポート（実施時のみ）
│   └── survey-validated.md ← 検証済み調査（実施時のみ）
└── prototype/             ← プロトタイプ実装（実施時のみ、隔離スペース）
    ├── {試したコード一式}
    └── prototype-report.md ← 実験結果サマリ
```

`{slug}` は要望の短い英語スラッグ（kebab-case, 30 文字以内）。

## 実行フロー

### Phase 1: 初期要望の受領

1. 引数があればそのまま初期要望として受領
2. 引数がなければ `AskUserQuestion` で「どんなことを実現したいか」を聞く
3. 受領した要望を `interview-log.md` の冒頭に記録

### Phase 2: 段階的ヒアリング

メインエージェントがインタビュアーとして、以下の観点を順次 `AskUserQuestion` で確認する。
**1 観点ずつ**、回答を踏まえて次の質問を決める。回数に制限なし、不明な点は必ず聞く。

#### ヒアリング観点（順序）

1. **機能要件の核**: 「具体的にどういう操作・機能が必要か」
2. **想定ユーザー**: 「誰が使うのか（役割・知識レベル）」
3. **スコープの境界**: 「どこまでをやり、どこからはやらないか」
4. **優先度**: 「必須 / 重要 / あると良い をどう分けるか」
5. **制約**: 「技術スタック / 期限 / 既存システムとの関係 など」
6. **非機能要件**: 「パフォーマンス・セキュリティ・可用性で気にする点はあるか」（該当時のみ）
7. **受け入れ条件**: 「どうなったら完成と言えるか」

#### ヒアリングの進め方

- 各回答を `interview-log.md` に追記する
- 既に明確な観点はスキップ
- 回答が曖昧 / 追加情報が必要な場合は深掘り質問を遠慮なく重ねる
- ユーザーが「お任せ」を選んだ項目は仕様書で `[未解決]` マークを付ける
- ユーザーから「もう十分」と意思表示があれば Phase 3 へ
- 観点 1〜7 を一通り終えたら自動的に Phase 3 へ

### Phase 3: 既存実装調査（フィジビリ調査）

`AskUserQuestion` で「既存コードベースを調査するか」を確認 (Recommended: Yes)。
スキップする選択肢: 「新規プロジェクト / 既存に関連実装が無いことが明白」な場合。

実施する場合:

1. `zeus-explorer` を起動 (必要なら領域を分けて複数並列)
2. プロンプト:
   - Phase 1-2 で確定した要望と機能要件
   - 「実装したい機能に関連する既存コード・抽象化レイヤー・規約を調査せよ。**仕様策定の参考になる範囲で深さ重視**」
3. 生レポートを `raw/explorer.md`（並列時は `explorer-1.md` `explorer-2.md` ...）に全文保存
4. 結果を踏まえて Phase 2 に戻って追加ヒアリングが必要か判断
   - 既存パターンと食い違う要望があれば `AskUserQuestion` で「合わせる / 上書きする」を確認

### Phase 4: フィジビリティ調査（外部情報 + 必要ならプロトタイプ）

「実現できそうか」「どんなアプローチがあるか」「ハマりどころは何か」を確認するフェーズ。
2 段階に分かれる:

#### 4-A: 外部情報調査 + 技術選定

`AskUserQuestion` で「外部情報を調査するか」を確認 (Recommended: Yes)。
スキップする選択肢: 「既存スタック内で完結 / 自明な実装」な場合。

このフェーズはフィジビリティ調査と技術選定の両方を担う。

実施する場合:

1. `zeus-tech-surveyor` を起動
2. プロンプト:
   - Phase 1-2 の要望と機能要件
   - Phase 3 の既存実装調査結果（実施した場合）
   - プロジェクト `CLAUDE.md` の関連抜粋（既存スタック制約があれば）
   - 「この機能を実装する際の関連ライブラリ / 公式推奨パターン / 知られた落とし穴 / 似たユースケースの実装例を WebSearch / WebFetch で調査せよ。**実現可能性を判断する材料を集めると同時に、複数候補がある場合は観点別に比較すること**」
3. 生レポートを `raw/survey.md` に全文保存
4. `zeus-survey-validator` を起動して出典・鮮度を検証、`raw/survey-validated.md` に全文保存
5. **採用候補の決定**:
   - 候補が 1 つしかない / 推奨が明確 → そのまま採用としてメインが採用理由・注意点を整理
   - 候補が複数で判断が割れる → `AskUserQuestion` で「どの候補を採用するか」を選ばせる
6. 採用が決まったら、後段の Phase 6 で spec.md に以下の形で反映するための情報をメモしておく:
   - 採用候補名 + バージョン
   - 選定理由（要件・制約に照らした 1〜2 文）
   - 採用時の注意点（バージョン互換性、依存、ライセンス、運用上の注意など）

#### 4-B: プロトタイプ実装（任意）

`AskUserQuestion` で「実現可能性を確かめるプロトタイプを試すか」を確認 (Recommended: No、ただし以下に該当するなら Yes 推奨):
- 不確定な技術要素がある (新規ライブラリ / 試したことのない API / パフォーマンス懸念)
- 4-A で「実装パターンが複数提示されたがどれが筋か不明」
- 「動かしてみないと分からない」と感じる論点がある

実施する場合:

1. **隔離スペース** `.claude/zeus/specs/{ts}-{slug}/prototype/` を作成 (既存コードベースを汚さない)
2. 必要最小限のコードを書いて動かす:
   - 既存コードベースに統合する必要があれば最小の touch のみ
   - 主目的は「動くか / 期待した振る舞いか / どこで詰まるか」を確認すること
3. 結果を `prototype/prototype-report.md` に記録:

```markdown
# プロトタイプ実装結果

- 試した時刻: {YYYY-MM-DD HH:MM:SS}
- 目的: {何を確認したかったか}

## 試したコード
{ファイル一覧と概要}

## 動作結果
{動いた / 動かなかった / 部分的に動いた}

## 確認できたこと
- {1 行サマリ}

## 課題として残った点
- {dev で考慮すべきポイント}

## 採用推奨アプローチ
{プロトタイプを踏まえて、本実装でどう書くべきか}
```

4. プロトタイプは spec 完了後も `prototype/` に残す。本実装は `/zeus:dev` で別途行う (プロトタイプを参考にしつつ、本実装は本実装としてやり直す)

#### 結果を反映

4-A / 4-B どちらかでも実施した場合、結果を踏まえて Phase 2 に戻って追加ヒアリングが必要か判断:
- フィジビリ調査で「ユーザー要望が実現困難 / 想定より大規模」と分かれば `AskUserQuestion` で「スコープ縮小 / 別アプローチ / そのまま進める」を確認

### Phase 5: ヒアリングログ整理

`interview-log.md` を以下の形式で完成させる:

```markdown
# ヒアリングログ

- 開始: {YYYY-MM-DD HH:MM:SS}
- 完了: {YYYY-MM-DD HH:MM:SS}

## 元の要望
{ユーザーの最初の発言}

## 質問と回答

### Q1: {観点}
- 質問: {実際に投げた質問文}
- 回答: {ユーザーの回答内容}

### Q2: ...

## 調査結果（実施した場合）
- 既存実装調査: raw/explorer.md
- ベストプラクティス調査: raw/survey-validated.md
```

### Phase 6: zeus-spec-writer 起動

`zeus-spec-writer` を 1 体起動。プロンプトには以下を含める:

- 元の要望
- `interview-log.md` の全文
- `raw/explorer.md` の全文（実施時のみ）
- `raw/survey-validated.md` の全文（実施時のみ）
- Phase 4-A で決定した採用候補・選定理由・注意点（実施時のみ）
- プロジェクトコンテキスト（CLAUDE.md の関連部分）
- 「ヒアリングと調査結果を統合した構造化された仕様書を作成せよ。既存実装の状況・技術的方向性・採用技術（あれば）も spec.md に反映すること」

spec.md には以下を必ず含めること:

**(1) 関連調査リソース セクション** (冒頭付近)

`/zeus:dev` 側が再利用するため、調査結果のファイルパスを明示する:

```markdown
## 関連調査リソース

- 既存実装調査: raw/explorer.md（実施時のみ。dev の Phase 2 で再利用される）
- ベストプラクティス調査: raw/survey-validated.md（実施時のみ）
- プロトタイプ: prototype/prototype-report.md（実施時のみ）
```

**(2) 技術スタック サブセクション** (「## 5. 制約」末尾、技術選定を実施した場合のみ)

```markdown
### 技術スタック（Phase 4-A で確定）

- 採用: {候補名 vX.Y.Z}
- 選定日: {YYYY-MM-DD}
- 調査レポート: raw/survey-validated.md
- 主な理由: {1〜2 文}
- 採用時の注意点: {重要な注意点があれば}
```

応答を省略せず全文 `.claude/zeus/specs/{ts}-{slug}/spec.md` に保存。

### Phase 7: 仕様書サマリ提示

`spec.md` の主要セクション（要望の本質 / 機能要件 / スコープ / 制約 / 受け入れ条件 / 未解決の論点）を要約してテキスト出力する。

ユーザーから修正要望があれば Phase 2 または Phase 3 / 4 に戻る。
修正要望が無ければ Phase 8 へ。

### Phase 8: 次アクション選択

`AskUserQuestion` で次のアクションを確認:

- **`/zeus:dev` に進む（橋渡し）**: 仕様書を入力に「計画策定 → 実装 → セルフレビュー」を一気通貫実行
- **ローカル保存のみで終了**

### Phase 9: /zeus:dev への橋渡し（選択時）

中間ファイル (旧 `plan-handoff.md`) は生成しない。`Skill` ツールで `zeus:dev` を起動し、引数に **`spec.md` のパスを直接渡す**。

dev 側の Phase 1 で spec.md を Read してタスク詳細・採用技術・既存実装との関係を取り込み、Phase 2 で同ディレクトリ配下の `raw/explorer.md` をそのまま再利用する (= dev は explorer を改めて起動しない)。これにより spec ↔ dev の二重 explorer を削減する。

引数例:

```
Skill(skill="zeus:dev", args="以下の仕様書を実装する。詳細は .claude/zeus/specs/{ts}-{slug}/spec.md を参照: {1 行サマリ}")
```

## 動作原則

- **EnterPlanMode は使わない**: bypassPermissions モードと両立させるため
- **不明な論点は必ず AskUserQuestion で確認**: 回数に制限なし。「曖昧なまま進める」より「ユーザーに聞く」を優先
- **未解決は隠さない**: 答えが出なかった項目は仕様書で `[未解決]` 明示
- **生レポート保存厳守**: ヒアリングログ・仕様書・調査結果は全文保存
- **フィジビリ調査は spec で済ませる**: dev での差し戻しを減らすため、Phase 3/4 の調査を惜しまない
