# Zeus Spec スキル（仕様策定担当）

ざっくりした要望を **対話的なヒアリング** で具体化し、後続の `/zeus:plan` が消費できる構造化された仕様書を作るスキル。
要件が固まる前に `/zeus:plan` に行くと曖昧なまま実装計画が立つので、その前段として使う。

zeus プラグインは 4 スキルで構成される:

- **`/zeus:spec`**（このスキル）: 要件定義・仕様策定
- **`/zeus:plan`**: 仕様や明確なタスクから実装計画策定
- **`/zeus:dev`**: plan.md を入力に実装＋セルフレビュー
- **`/zeus:review`**: 単独レビュー（plan に橋渡し可能）

## 引数仕様

| 呼び出し | 動作 |
|---|---|
| `/zeus:spec <要望>` | 引数を初期要望として受領、ヒアリング開始 |
| `/zeus:spec` | 引数なしの場合は `AskUserQuestion` でまず「何がしたいか」を聞く |

## 使用エージェント

| エージェント | subagent_type | 役割 |
|---|---|---|
| Zeus Spec Writer | `zeus-spec-writer` | ヒアリング結果を構造化された仕様書に整理 |

ヒアリング自体は **メインエージェント（あなた）** が `AskUserQuestion` を使って進める。

## ディレクトリ規約

仕様書は以下に保存:

```
.claude/zeus/specs/{YYYYMMDD-HHMMSS}-{slug}/
├── spec.md            ← zeus-spec-writer が作成（メイン成果物）
├── interview-log.md   ← ヒアリングのやりとり記録
└── plan-handoff.md    ← /zeus:plan への引き継ぎ（橋渡し時のみ）
```

`{slug}` は要望の短い英語スラッグ（kebab-case, 30 文字以内）。

## 実行フロー

### Phase 1: 初期要望の受領

1. 引数があればそのまま初期要望として受領
2. 引数がなければ `AskUserQuestion` で「どんなことを実現したいか」を聞く
3. 受領した要望を `interview-log.md` の冒頭に記録

### Phase 2: 段階的ヒアリング

メインエージェント（あなた）が **インタビュアー** として、以下の観点を順次 `AskUserQuestion` で確認する。
**重要**: 一度に全部聞かない。**1 観点ずつ**、回答を踏まえて次の質問を決める。

#### ヒアリング観点（順序）

1. **機能要件の核**: 「具体的にどういう操作・機能が必要か」
2. **想定ユーザー**: 「誰が使うのか（役割・知識レベル）」
3. **スコープの境界**: 「どこまでをやり、どこからはやらないか」
4. **優先度**: 「必須 / 重要 / あると良い をどう分けるか」
5. **制約**: 「技術スタック / 期限 / 既存システムとの関係 など」
6. **非機能要件**: 「パフォーマンス・セキュリティ・可用性で気にする点はあるか」（該当時のみ）
7. **受け入れ条件**: 「どうなったら完成と言えるか」

#### ヒアリングの進め方

- 各回答を `interview-log.md` に追記する
- 既に明確な観点はスキップ（過剰な質問は避ける）
- 回答が曖昧な場合は **追加質問** で深掘りする（最大 2 段階まで）
- ユーザーが「お任せ」を選んだ項目は仕様書で `[未解決]` マークを付ける
- ユーザーから「もう十分」と意思表示があれば即座にヒアリング終了

#### 中断・終了の判断

- ユーザーが `Ctrl+C` 相当の操作で中断した場合は、ここまでの内容を保存して終了
- 「ヒアリングはここまでで OK」と言われたら Phase 3 へ
- 観点 1〜7 を一通り終えたら自動的に Phase 3 へ

### Phase 3: ヒアリングログ整理

`interview-log.md` を以下の形式で完成させる:

```markdown
# ヒアリングログ

- 開始: {YYYY-MM-DD HH:MM:SS}
- 完了: {YYYY-MM-DD HH:MM:SS}

## 元の要望
{ユーザーの最初の発言}

## 質問と回答

### Q1: {観点}
- 質問: {実際に投げた質問文}
- 回答: {ユーザーの回答内容}

### Q2: ...
```

### Phase 4: zeus-spec-writer 起動

`zeus-spec-writer` を 1 体起動する。
プロンプトには以下を含める:

- 元の要望
- `interview-log.md` の全文
- プロジェクトコンテキスト（必要なら CLAUDE.md の関連部分の引用）
- 「上記情報を構造化された仕様書として整理せよ」

`zeus-spec-writer` は出力ガイダンスに従って仕様書を返す。

応答を **省略せず全文** 以下に保存:

```
.claude/zeus/specs/{ts}-{slug}/spec.md
```

### Phase 5: 仕様書承認

`spec.md` 本文を `EnterPlanMode` に渡して承認 UI を表示する。
（CLAUDE.md ルール: 「方針承認はテキストではなく EnterPlanMode で」）

ユーザーから修正要望があれば、Phase 2 のヒアリングに戻って該当箇所を再確認する。

### Phase 6: 次アクション選択

仕様書承認後、`AskUserQuestion` で次のアクションを確認:

- **`/zeus:plan` に進む（橋渡し）**: 仕様書を入力に実装計画策定へ
- **ローカル保存のみで終了**: 仕様書は保存済み、後で別途 `/zeus:plan` を呼べる

### Phase 7: /zeus:plan への橋渡し（選択時）

橋渡しを選んだ場合:

1. `spec.md` から修正・実装に必要な情報を整理し、`plan-handoff.md` に保存:

```markdown
# /zeus:plan への引き継ぎ

- 元仕様書: .claude/zeus/specs/{ts}-{slug}/spec.md

## 実装タスク（spec.md ベース）

{spec.md の機能要件・非機能要件・スコープを plan が消費しやすい形に変換}

## 制約・優先度

{spec.md の制約セクションから、plan が考慮すべき項目を抽出}

## 未解決の論点（plan で判断が必要）

{spec.md の未解決論点をそのまま転記}
```

2. `Skill` ツールで `zeus:plan` を起動し、引数として `plan-handoff.md` のパスと 1 行サマリを渡す:
   - 引数例: 「以下の仕様書を実装する。詳細は `.claude/zeus/specs/{ts}-{slug}/plan-handoff.md` を参照: {1 行サマリ}」
3. 通常の `/zeus:plan` フロー（explorer → architect → critique → plan-reviewer → 統合）に合流

## 動作原則

- **段階的にヒアリング**: 一度に全部聞かない。1 観点ずつ確認
- **過剰な質問はしない**: 既に明確な観点はスキップ
- **ユーザーの意図を抽出**: 言葉通りではなく本質を読む（仕様書化は zeus-spec-writer が担当）
- **未解決は隠さない**: 答えが出なかった項目は仕様書で明示
- **テキストでの承認質問は禁止**: 必ず `AskUserQuestion` / `EnterPlanMode` を使う
- **生レポート保存厳守**: ヒアリングログ・仕様書は全文保存

## 他スキルとの使い分け

| スキル | 用途 |
|---|---|
| **`/zeus:spec`** | **要望が曖昧な状態で、要件を対話的に詰めたい時** |
| `/zeus:plan` | 要件が明確で、実装計画を立てたい時 |
| `/zeus:dev` | plan.md があり、実装に進む時 |
| `/zeus:review` | 既存コード・PR・diff のレビュー |

要件が明確なら `/zeus:spec` をスキップして直接 `/zeus:plan` を呼ぶ方が速い。
逆に「やりたいことは漠然としてる」「実装範囲を詰めたい」場合は `/zeus:spec` から始める。
